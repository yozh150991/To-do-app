# ADR-002: Переходи повторів рахує спільне KMP-ядро, сервер лише перевіряє інваріанти

- **Статус:** Accepted
- **Дата:** 1 листопада 2026 року
- **Власник рішення:** власник проєкту
- **Замінює у v2.6.1:** §8.1.0 (FIX-03) повністю; Ф5b (роботи й критерій для `complete`/`skip`); §12.1 (Backend integration — частина про Deno evaluator і паритет Kotlin/Deno); §16 (TR-17)

## Контекст

- FIX-03 запровадив «довірений» серверний розрахунок наступної появи: клієнт отримує `requires_server_evaluation`, а Supabase Edge Function `evaluate_recurrence` на TypeScript/Deno заново обчислює перехід, і тільки цей план приймає `apply_ops`.
- Так з'являється **друга реалізація** recurrence engine (§4.0.1 і §4.3) з окремим корпусом паритету Kotlin/Deno. Це суперечить:
  - причині вибору Kotlin Multiplatform — одне ядро для Android, Desktop і Web;
  - правилу §9.1, за яким імпортер на TypeScript не дублює Kotlin-парсер.
- Бази часових поясів (tzdb) на Android/JVM і в Deno оновлюються незалежно. FIX-03 при розбіжності вимагає відхиляти мутацію, тож коректні дії користувача відкидатимуться через різні версії tzdb.
- Застосунок має одного користувача, а всі клієнти — його власні збірки. Серверний перерахунок не захищає від реальної загрози. Реальні ризики інші:
  - дві дії над однією появою з різних пристроїв;
  - застарілий клієнт зі старою семантикою повторів.

  Обидва закриваються перевірками на сервері без власного календарного розрахунку.

## Рішення

1. **Єдине ядро.** Усі клієнти обчислюють переходи (`complete`, `skip_to_next`, `reschedule_current`, `edit_recurrence_rule`, `stop`, Undo) однією функцією `nextOccurrence` з `commonMain` (§4.0.1, п. 7). Android, Desktop і Web виконують той самий код.
2. **Команда з готовим планом.** `sync_push` приймає типізовану recurrence-команду: `operation_id`, `occurrence_id`, очікуваний стан появи, `base_revision`, `recurrence_policy_version`, `action_at` (UTC), `action_zone_id` (IANA), `tzdb_version` (для діагностики) і результат переходу — нову появу (`scheduled_for`, `effective_due`) або `null`, а також запис completion/skip.
3. **Сервер не рахує календар.** Gateway (`apply_ops` під тим самим advisory lock) атомарно перевіряє:
   - власність, ідемпотентність за `operation_id`, epoch/handshake;
   - `revision` сутності дорівнює `base_revision`;
   - `occurrence_id` існує і перебуває в очікуваному стані;
   - `recurrence_policy_version` входить до серверного переліку підтримуваних версій;
   - після переходу лишається 0..1 активна поява і немає другого completion для тієї ж появи;
   - структурну коректність: валідні дата й зона, перехід дозволений таблицею станів §4.3.

   Лише після цього одним commit пишуться Task/Occurrence/Completion, activity, change log і receipt.
4. **Гонки.** Розбіжність ревізії чи стану появи → `already_applied` (той самий `operation_id`) або recoverable conflict у `ConflictRecovery`. Другий пристрій перечитує стан і перераховує перехід локально. Ні другої активної появи, ні дубля completion.
5. **Версія політики.** Будь-яка зміна семантики повторів підвищує `recurrence_policy_version`. Клієнт з непідтримуваною версією отримує `client_upgrade_required`; його операції лишаються pending і не губляться.
6. **tzdb.** `tzdb_version` записується в receipt для діагностики, але не є причиною відхилення.
7. **Імпорт без змін.** Імпортер Ф5.1 (TypeScript) повторів не рахує; конвертація йде через `ImportPending` на клієнті (§9.1).

## Наслідки

**Плюси**
- Одна реалізація recurrence engine; корпус паритету Kotlin/Deno і Edge Function `evaluate_recurrence` не потрібні.
- Ф5b стає меншою: зникають `requires_server_evaluation`, окремий маршрут через Edge і тести stale plan для Edge.
- Немає хибних відмов через різні версії tzdb.

**Мінуси та як їх компенсувати**
- Сервер довіряє арифметиці клієнта: помилка в ядрі дасть неправильну дату, яку сервер прийме. Компенсація:
  - golden fixtures TIME-01..TIME-08 і property-тести проганяються в CI на всіх KMP-таргетах (Android, JVM, Wasm);
  - `recurrence_policy_version` блокує клієнтів зі старою семантикою;
  - історія операцій дозволяє виправити дату звичайним редагуванням.
- Якщо колись з'являться сторонні клієнти чи кілька користувачів, рішення переглядається окремим ADR.

## Перевірка (замінює критерій Ф5b для `complete`/`skip`)

- [ ] Два пристрої одночасно виконують або пропускають ту саму появу: одну операцію прийнято, друга отримує `already_applied` або recoverable conflict; жодної другої активної появи чи дубля completion.
- [ ] Команда із застарілою `base_revision` або чужим `occurrence_id` відхиляється без часткового запису.
- [ ] Клієнт із непідтримуваною `recurrence_policy_version` отримує `client_upgrade_required`, а його операції лишаються в outbox.
- [ ] Golden fixtures і property-тести recurrence зелені в CI на Android, JVM і Wasm.
- [ ] Прямий виклик `apply_ops` клієнтськими ролями заборонений (без змін щодо v2.6.1).

## Розглянуті альтернативи

- **Довірений Deno evaluator (FIX-03).** Друга реалізація ядра, паритетні тести, ризик хибних відмов через tzdb. Відхилено.
- **Компіляція KMP-ядра в JavaScript для Edge Function.** Одне ядро, але ускладнюється збірка й розгортання, а загрози, яку це закриває, немає. Лишається варіантом для майбутнього ADR, якщо з'являться сторонні клієнти.
- **Розрахунок у SQL на сервері.** Третя реалізація календарної логіки; відхилено ще у v2.6.1.
