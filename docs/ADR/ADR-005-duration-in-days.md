# ADR-005: Тривалість задачі в днях

- **Статус:** Accepted (власник обрав «додати тривалість у днях», 3 листопада 2026 року)
- **Дата:** 3 листопада 2026 року
- **Власник рішення:** власник проєкту
- **Стосується v2.6.1:** §4.1 (поле `duration_min`, тепер у `docs/DATA_MODEL.md`), §5.4 «Тривалість» (`docs/UX_SPEC.md`), §6.1 «Duration контракт Ф6b» (`docs/UX_SPEC.md`), §9.3 (мапінг `duration` у `docs/IMPORT_COVERAGE.md`)

## Контекст

- Специфікація знає лише тривалість у хвилинах: `Task.duration_min` для календаря й time blocking (Ф6b, 5–1 440 хвилин).
- Todoist зберігає тривалість як `duration { amount, unit }`, де `unit` — `minute` або `day` («на 3 дні»). Перевірка API перед імпортом Ф1a (`docs/IMPORT_COVERAGE.md`) показала, що задачі з тривалістю в днях без нового поля втратили б її або мали б її в іншому значенні.
- Переведення днів у хвилини (1 день = 1 440 хв) зберегло б число, але змішало б два різні поняття: «зайняти 3 години» і «тягнеться 3 дні».

## Рішення

1. **Нове поле `Task.duration_days`** (`int?`, ціле ≥ 1) поруч із `duration_min`. Задача має **або** тривалість у хвилинах, **або** в днях, **або** жодної: обидва поля одночасно заборонені (CHECK у схемі й перевірка в домені).
2. **Значення:** задача з датою `due_date` і `duration_days = N` триває N календарних днів, з `due_date` включно. Без `due_date` тривалість у днях зберігається, але ні на що не впливає (як `duration_min` без часу, §6.1).
3. **Фази:**
   - **Ф1a:** колонка в схемі v3 (міграція 2 → 3, додавання колонки, FIX-01), імпорт із Todoist (`unit = day` → `duration_days`), показ у деталях задачі текстом («3 дні»), backup/restore.
   - **Ф2:** граматика Quick Add — `на 3 дні`, `for 3 days`, `na 3 dni` → `duration_days`, поряд із хвилинами й годинами (§5.4).
   - **Ф6b:** календар малює задачу з `duration_days` смугою на N днів; контракт хвилин (5–1 440) не змінюється.
4. **Синхронізація (Ф5):** поле переходить у `field_patch` операцій `task` так само, як `duration_min`.

## Наслідки

- Додаткова колонка й одна перевірка «або хвилини, або дні»; без перебудови таблиці.
- Імпорт Todoist зберігає тривалість без втрат: `minute` → `duration_min`, `day` → `duration_days`.
- Нормативні файли оновлено разом із цим ADR: рядок `duration_days` у §4.1 (`docs/DATA_MODEL.md`), граматика днів у §5.4 і смуга днів у §6.1 (`docs/UX_SPEC.md`).

## Розглянуті альтернативи

- **Переводити дні в хвилини** (1 день = 1 440 хв): без зміни схеми, але календар Ф6b малював би 72-годинний блок замість смуги днів, а контракт 5–1 440 хвилин довелось би ламати.
- **Замінити `duration_min` парою `duration_amount` + `duration_unit`** (як у Todoist): точніше відтворює Todoist, але вимагає перебудови таблиці й зміни всіх місць, що вже спираються на `duration_min`.
- **Лише звіт імпорту, без поля:** найдешевше, але тривалість у днях губилась би після переходу з Todoist.

## Перевірка

- Ф1a: міграція v2 → v3 зберігає наявні `duration_min`; CHECK відхиляє обидва поля разом; імпорт фікстури Todoist з `unit = day` дає `duration_days`; backup → restore зберігає поле.
- Ф2: golden-фрази «на 3 дні» / «for 3 days» / «na 3 dni».
- Ф6b: смуга на N днів, включно з переходом через межу місяця.
