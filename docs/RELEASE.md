# Релізи Android APK

Нормативна основа — spec v2.6.1 §3.4. Канал встановлення й оновлення — [ADR-003](ADR/ADR-003-update-channel.md).

**Головне правило:** нова версія завжди встановлюється **поверх** старої тим самим ключем підпису. Видалити застосунок і поставити заново — означає втратити локальні дані. Без ключа підпису оновити встановлений застосунок неможливо.

## Як це влаштовано

| Що | Де |
| --- | --- |
| Ключ підпису (`todo-release.jks`, PKCS12, RSA 4096, alias `todo-release`) | На комп'ютері власника (`~/todo-release-key`) + дві резервні копії. Ніколи в git |
| Пароль ключа | Менеджер паролів |
| Відбиток сертифіката (SHA-256) | `.github/release-signing-cert.sha256` у репозиторії |
| **Основна збірка** | `tools/release/build-release.sh` на комп'ютері власника → `dist/todo-vX.Y.Z.apk` |
| **Запасна збірка** | `.github/workflows/release.yml` на push тегу `vX.Y.Z` → GitHub Releases (ключ у secrets середовища `release`) |
| Доставка на телефон | USB (`adb install -r`, пропонує скрипт) або файл через месенджер / хмару / кабель; встановлення системним інсталятором Android. Сторонніх застосунків-оновлювачів немає |
| Перевірка скриптів на кожному PR | `tools/ci/local-release-e2e.sh` з одноразовим ключем: Linux і Windows (Git Bash) |

Обидва шляхи збирають той самий код з `main`, підписують тим самим ключем і відмовляються видавати APK, якщо:
- збирається не `origin/main` або є незакомічені зміни (локально) / тег вказує на коміт поза `main` (GitHub);
- версія не новіша за останній реліз (або це `0.0.0`);
- APK підписаний іншим сертифікатом, ніж закріплений;
- `versionCode` / `versionName` у зібраному APK не збігаються з версією.

**Версії.** `versionName` = `X.Y.Z`. `versionCode` = `X × 1 000 000 + Y × 1 000 + Z`, тож зростає разом із версіями. Обидва шляхи для однієї версії дають однаковий `versionCode` і підпис, тому їхні APK ставляться один поверх одного. Debug-збірки мають `applicationId` з суфіксом `.debug` і ставляться поруч із робочою, не замінюючи її.

**ABI.** Release містить лише `arm64-v8a` (ADR-001: менший APK; усі сучасні телефони — arm64).

## Перше налаштування (один раз, робить власник)

### 1. Створити ключ

Потрібен `keytool`: він є в Android Studio і в будь-якому JDK, скрипт шукає його сам (`JAVA_HOME`, `PATH`, Android Studio, Temurin, Oracle, Microsoft JDK).

- **Windows** (потрібен Git for Windows): подвійний клік на `tools/release/create-keystore.sh` або в Git Bash `bash tools/release/create-keystore.sh`.
- **macOS / Linux:** у терміналі `bash tools/release/create-keystore.sh`.

Скрипт створює ключ у `~/todo-release-key` (на Windows — `C:\Users\<ім'я>\todo-release-key`), двічі просить пароль (символи не показуються, мінімум 12), друкує відбиток SHA-256, не перезаписує наявний ключ і не закриває вікно до натискання Enter.

### 2. Дві незалежні резервні копії

1. **Менеджер паролів:** запис «To-do app release key» з паролем, alias `todo-release`, відбитком SHA-256 і файлом `todo-release.jks` як вкладенням.
2. **Офлайн-носій:** зашифрований USB-накопичувач з тим самим файлом; пароль — в окремому місці.

Перевірити копію: `keytool -list -v -keystore <копія>.jks -alias todo-release` має показати той самий SHA-256.

### 3. Закріпити відбиток у репозиторії

PR, який замінює рядок з відбитком у `.github/release-signing-cert.sha256`. Зроблено 02.11.2026.

### 4. Android Studio на комп'ютері (для основної збірки)

1. Встановити Android Studio з `developer.android.com/studio`.
2. Відкрити її один раз і пройти майстер першого запуску (Standard): він завантажить Android SDK.

Більше в Android Studio нічого робити не треба: збирає скрипт. JDK і SDK він знаходить сам.

### 5. Secrets у GitHub (для запасної збірки)

Settings → Environments → **New environment** `release`:

- **Deployment branches and tags** → *Selected branches and tags* → правило для тегів `v*.*.*`.
- **Environment secrets:** `TODO_RELEASE_KEYSTORE_BASE64` (вміст `todo-release.jks.base64.txt`), `TODO_RELEASE_KEYSTORE_PASSWORD`, `TODO_RELEASE_KEY_ALIAS` (`todo-release`), `TODO_RELEASE_KEY_PASSWORD` (той самий пароль).

Після цього видалити `todo-release.jks.base64.txt`. Якщо запасний шлях стане не потрібен — видалити середовище `release` разом із secrets; основний шлях від нього не залежить.

## Випуск версії (основний шлях: збірка на комп'ютері)

1. Злити в `main` усі PR, які мають увійти в реліз (разом із записом у `CHANGELOG.md`).
2. У папці репозиторію запустити скрипт:
   - **Windows:** подвійний клік на `tools/release/build-release.sh` або Git Bash → `bash tools/release/build-release.sh`;
   - **macOS / Linux:** `bash tools/release/build-release.sh`.

   Версію можна передати аргументом (`bash tools/release/build-release.sh 0.1.0`) або ввести, коли скрипт запитає.
3. Скрипт:
   - отримує свіжий `origin/main` і перевіряє, що поточна папка — саме він, без змін; якщо локальна копія просто відстає (після злиття PR на GitHub), пропонує оновити її сам і просить запустити скрипт ще раз;
   - перевіряє, що версія новіша за останній тег;
   - просить пароль ключа і **до збірки** звіряє ключ із закріпленим відбитком;
   - збирає APK (перша збірка 10–15 хвилин, далі — 1–3);
   - перевіряє підпис, версію й ABI в готовому APK;
   - кладе `dist/todo-vX.Y.Z.apk` і `.sha256` та відкриває папку `dist`;
   - створює тег `vX.Y.Z` і пропонує відправити його на GitHub (тоді GitHub збере запасну копію в Releases);
   - якщо телефон підключено кабелем із увімкненою налагодженням по USB — пропонує встановити APK одразу.
4. Якщо щось не так, скрипт зупиняється, повторює причину в останніх рядках вікна й чекає Enter. Усе, що він виводив, — у `dist/build-release-last.log` (цей файл можна просто надіслати); лог самої Gradle-збірки — `dist/build-vX.Y.Z.log`.

## Запасний шлях: збірка на GitHub

Відправка тегу `vX.Y.Z` (скриптом на кроці 3 або вручну) запускає workflow **Release**: той самий код, той самий ключ із secrets, ті самі перевірки. Через ~15 хвилин на сторінці **Releases** репозиторію з'являється `todo-vX.Y.Z.apk` і `.sha256`. Створювати реліз вручну через UI не треба.

Тег вручну (Git Bash у папці репозиторію; Windows: правий клік → *Open Git Bash here*):

```bash
git checkout main && git pull
git tag -a v0.1.0 -m "v0.1.0"
git push origin v0.1.0
```

Тег на конкретний коміт `main`: `git tag -a v0.1.0 <sha> -m "v0.1.0"`. Без командного рядка (GitHub Desktop): *Fetch origin* → **History** → правий клік на коміті → **Create Tag…** → **Push origin**.

## Встановлення й оновлення на телефоні

Без сторонніх застосунків (ADR-003). Будь-який із способів; завжди **поверх** наявної версії:

- **Кабель USB (найшвидше).** Один раз: на телефоні *Налаштування → Про телефон → 7 разів натиснути «Номер збірки»*, потім *Для розробників → Налагодження по USB*. Підключити кабель, дозволити комп'ютер на телефоні. Далі `build-release.sh` сам запропонує встановити.
- **Файлом.** Надіслати собі `dist/todo-vX.Y.Z.apk` (Telegram «Збережене», Google Drive тощо) або скопіювати кабелем → відкрити файл на телефоні → **Встановити / Оновити**. Уперше Android попросить дозволити встановлення з цього застосунку (Telegram, Файли, Chrome) — дозволити.
- **Із GitHub Releases (запасний шлях).** У браузері телефона відкрити сторінку Releases репозиторію → завантажити `todo-vX.Y.Z.apk` → відкрити.

Якщо Android пише, що застосунок «не встановлено» через конфлікт підпису, **нічого не видаляти**: це означає, що APK підписаний іншим ключем. Спершу розібратися з ключем.

**Ніколи** не видаляти застосунок, щоб «поставити начисто», якщо немає свіжого backup (з Ф1a — експорт у налаштуваннях).

## Відновлення ключа

- **Новий комп'ютер:** скопіювати `todo-release.jks` з резервної копії в `~/todo-release-key/`, звірити SHA-256 із закріпленим — і `build-release.sh` працює як раніше.
- **Втрачено GitHub-secrets:** заново заповнити з резервної копії (крок 5).
- **Втрачено ключ повністю (обидві копії):** оновити встановлений застосунок неможливо. Порядок: експорт backup у старому застосунку → новий ключ → PR зі зміною відбитка (окреме рішення власника) → видалити старий застосунок → встановити новий → відновити backup. Тому копій дві й вони незалежні.
